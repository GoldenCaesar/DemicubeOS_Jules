A keyboard-driven desktop relies on an input router and a window management state rather than standard mouse event listeners.

### Architecture Overview

```
                        [ Global Keydown Listener ]
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼                                       ▼
       [ Window Cycling Layer ]               [ Input Focus Router ]
       (Alt+Tab / Alt+A / Alt+D)              (Active Window / Shell)
                 │                                       │
                 ▼                                       ▼
       Updates z-index / CSS              Executes CLI Command or Sub-app
     (Notepad, Browser, Terminal)         (e.g., "zoom 150%", "open log.txt")

```

---

### Recommended Tech Stack

| Layer | Tool / Library | Role |
| --- | --- | --- |
| **Framework** | **Svelte 5** | Handles dynamic UI and window docking with zero runtime overhead; compiles to lean vanilla JS. |
| **Terminal Core** | **xterm.js** | Handles raw keyboard buffers, ANSI color rendering, and text selection natively. |
| **Keybindings Engine** | **Mousetrap** (or native key listeners) | Traps OS-level shortcuts (`Alt+Tab`, `Alt+A`, `Alt+D`) and isolates application shortcuts. |
| **Cross-Platform Wrapper** | **Tauri 2** | Compiles the web app to native binaries for Steam (Windows/Linux) and Android, using ~15MB RAM compared to Electron's 150MB+. |

### Core Technical Directives for Developer

**1. Window Management & Tiling (CSS/State)**

* Build a `WindowManager` store holding an array of active windows: `{ id, appType, isMaximized, zIndex, contextState }`.
* Cycle active windows via `Alt+A` (previous) and `Alt+D` (next) by dynamically shifting `zIndex` values.
* Split the viewport using CSS Grid with a fixed dock for the persistent CLI prompt, while letting the main workspace expand or switch views via state.

**2. Persistent Terminal Input Routing**

* All keyboard events default to a central `InputDispatcher`.
* The terminal accepts system-wide shell commands (e.g., `cat`, `nmap`, `hydra`, `clear`).
* If an interactive sub-application is focused (e.g., a simulated browser or text editor), the CLI prompt prefixes contextual sub-commands (e.g., `browser:goto 10.0.0.1`, `browser:zoom 1.5`, `edit:save`).

**3. Program Registry Interface**

* Implement a simple executable pattern:

```typescript
interface InGameApp {
  id: string;
  name: string;
  render: () => HTMLElement;
  handleCommand: (args: string[]) => void;
}

```

* Adding a new application only requires registering a new implementation of `InGameApp` without altering the rendering loop.

**4. Browser and System Interception**

* Intercept `e.preventDefault()` on all target keystrokes (`Tab`, `Alt`, Arrow keys) at the document root to keep focus inside the simulated OS.
* Simulated browser windows should run as local sandboxed HTML/CSS mockups rather than actual `iframe` tags to allow direct styling and custom keyboard zooming.
